# 공지사항 숫자형 공개 번호 설계

## 1. 결정

공지사항 URL 식별자는 관리자가 입력하는 슬러그에서 DB가 자동 발급하는 양의 정수 공개 번호로 변경합니다.

- 국문 상세 주소: `/notices/{publicNumber}`
- 영문 상세 주소: `/en/notices/{publicNumber}`
- 내부 기본키 UUID는 관계와 관리자 명령에 계속 사용합니다.
- 공개 번호는 공지 생성 시 PostgreSQL identity가 원자적으로 발급하며 관리자가 입력하거나 수정할 수 없습니다.
- 국문과 영문은 같은 공개 번호를 사용하고 게시 상태만 독립적으로 유지합니다.

## 2. 대안 검토

1. **별도 공개 번호 identity — 채택:** 내부 UUID와 공개 주소의 책임을 분리하고 동시 생성에서도 중복되지 않습니다.
2. **현재 공지 수에 1을 더해 번호 계산 — 제외:** 동시 요청에서 같은 번호가 생길 수 있고 삭제·롤백에 취약합니다.
3. **제목 기반 슬러그 자동 생성 — 제외:** 공지는 사람이 읽는 주소의 이점보다 운영 단순성과 주소 불변성이 중요하며 한·영문 제목 선택 문제도 남습니다.

공개 번호는 연속 번호처럼 증가하지만, 실패한 트랜잭션 등으로 중간 번호가 비어 있을 수 있습니다. 번호의 연속성은 업무 규칙으로 보장하지 않습니다.

## 3. 데이터와 마이그레이션

`notices.public_number`에 `integer GENERATED ALWAYS AS IDENTITY`와 고유·필수 제약을 추가합니다. 기존 행은 생성일과 UUID 순서로 양의 정수를 한 번만 배정하고, identity 시퀀스는 기존 최댓값 다음부터 발급하도록 맞춥니다.

기존 `notice_slugs`는 마이그레이션에서 삭제하지 않습니다. 새 공지 생성과 수정에서는 더 이상 슬러그 행을 만들거나 변경하지 않고, 기존 주소 호환 조회에만 사용합니다. 운영 데이터와 외부 링크의 전환이 확인된 뒤 별도 승인 작업에서 제거할 수 있습니다.

## 4. 공개 조회와 주소 호환

목록, 상세, 첨부 다운로드와 팝업 공지의 상세 링크는 모두 공개 번호를 사용합니다. 상세 경로의 값이 양의 정수이면 `public_number`로 조회합니다.

기존 비숫자 슬러그로 공개 중인 공지를 찾으면 같은 로케일의 숫자 주소로 `308 Permanent Redirect`합니다. 존재하지 않는 값, 보관된 공지, 현재 로케일에 게시되지 않은 공지는 기존과 같이 404를 반환합니다. 숫자형 과거 슬러그는 공개 번호를 먼저 조회하고, 일치하는 공개 번호가 없을 때만 과거 슬러그로 조회합니다.

## 5. 관리자와 API

- 새 공지 화면에서 슬러그 입력란을 제거합니다.
- 생성·저장 API와 `NoticeCommandInput`에서 `slug`를 제거합니다.
- 생성 응답과 관리자 조회에는 읽기 전용 `publicNumber`를 포함합니다.
- 편집 화면은 `공지 번호 {publicNumber}`와 숫자형 공개 주소를 표시합니다.
- 슬러그 변경 API와 서비스 명령은 제거합니다.
- 관리자 목록과 공개 목록은 `notice_slugs` 내부 조인에 의존하지 않습니다.

## 6. 오류 처리

- 양의 정수가 아니거나 JavaScript 안전 정수 범위를 벗어난 경로 값은 공개 번호로 조회하지 않습니다.
- 공개 번호 중복은 DB 고유 제약으로 차단합니다.
- identity가 발급한 번호는 수정·재사용하지 않습니다.
- 관리자 입력 검증은 슬러그 존재 여부를 요구하지 않습니다.

## 7. 검증

1. 스키마 테스트에서 공개 번호 identity와 고유 제약을 확인합니다.
2. 생성 계약 테스트에서 슬러그 없이 공지가 생성되고 공개 번호가 반환되는지 확인합니다.
3. 공개 쿼리 테스트에서 숫자 번호 조회와 과거 슬러그 호환 조회를 확인합니다.
4. 관리자 화면 테스트에서 `슬러그` 입력이 없고 요청 본문에도 `slug`가 없는지 확인합니다.
5. 타입 검사, 린트, 관련 단위·DB 테스트와 프로덕션 빌드를 실행합니다.
6. 브라우저에서 공지를 생성한 뒤 `/notices/{publicNumber}` 공개 링크를 확인합니다.

## 8. 범위 제외

- 뉴스 슬러그 정책은 변경하지 않습니다.
- 공지 번호를 표시일이나 게시 순서로 다시 정렬하지 않습니다.
- 번호 누락을 메우거나 보관된 공지 번호를 재사용하지 않습니다.
- 기존 입찰공고를 공지사항으로 자동 이전하지 않습니다.

## 9. 자체 검토

- 미정 값이나 자리표시자는 없습니다.
- 관리자 입력 제거, DB 발급, 공개 조회와 과거 주소 호환이 같은 공개 번호 계약을 사용합니다.
- 변경 범위는 공지사항 식별자와 직접 연결된 문서·스키마·API·화면·테스트로 제한합니다.
