- 팝업 공개 조회에서 검사 완료 이미지의 공개 URL을 반환하고, 관리자 미리보기에서 실제 팝업 컴포넌트를 사용합니다.
- 계정 정보 확인, 비밀번호 변경, 로그아웃을 연결하고 운영 환경의 비밀번호 재설정 메일을 SMTP로 발송하도록 구성했습니다.
- 관리자 변경 API에 동일 출처 검사를 적용하고, 폼 오류·성공 안내와 미저장 변경 경고를 공통 처리합니다.

문서 첨부는 승인된 악성 파일 검사기가 없어 계속 비활성화 상태로 명시했습니다. 이번 후속 작업에서는 Docker와 관리자 DB 실행을 다루지 않았으므로 인증 후 브라우저와 실제 DB 게시 흐름은 실행 환경이 준비된 뒤 별도로 확인해야 합니다.

현재 관리자는 개발자 도움 없이 콘텐츠를 작성·수정·게시하는 업무를 끝낼 수 없는 상태입니다. 입력 문구뿐 아니라 편집, 카테고리 선택, 언어별 게시, 미리보기와 목록 조회에 결손이 있습니다. 아래 결과는 현재 소스에서 확인한 사항이며 최근 변경으로 생긴 회귀라고 단정하지 않습니다.

## 확인 범위와 기준

브라우저에서는 `/admin`이 로그인 화면으로 이동하고 이메일·비밀번호 입력과 로그인 버튼이 표시되는 것까지 확인했습니다. 관리자용 DB가 실행되지 않았고 인증된 세션이 없어 로그인 후 실제 클릭, 생성, 게시, 파일 업로드, 반응형 화면은 검증하지 않았습니다. 아래의 업무 흐름은 소스에서 추적한 결과이며 인증 후 브라우저 재현 완료를 뜻하지 않습니다.

기존 관련 테스트 6개 파일, 15개 테스트는 통과했습니다. 테스트 대상은 운영 현황, 공지 슬러그 입력 제거, 공지 공개 번호·주소·게시 정책, 공개 팝업 컴포넌트입니다. 관리자 편집 전체 흐름, 실제 DB 게시와 파일 저장소 통합은 이 검증에 포함되지 않습니다.

## 주요 발견

### 1. 우선 수정 — 뉴스·공지·팝업의 편집 화면에서 내용을 수정할 수 없습니다

- 업무 흐름: 새 글 작성 → 초안 저장 → 기존 항목 편집.
- 실제 구현: 뉴스는 슬러그·버전과 설명만 표시합니다. 공지와 팝업은 일부 상태 버튼만 표시하고 제목·본문 입력과 저장 버튼이 없습니다.
- 영향: 초안을 저장한 뒤 오탈자를 고치거나 내용을 보완할 수 없습니다. 뉴스는 화면에서 게시·숨김·보관도 처리할 수 없습니다.
- 공지는 보관 버튼이 있지만 복원 버튼이 없고, 팝업에는 보관·복원 버튼 모두 없습니다.
- 개선 방향: 기존 내용 로드, 수정, 저장, 언어별 상태 전환이 이어지는 편집 흐름을 완성해야 합니다.

### 2. 우선 수정 — 공지 카테고리를 내부 ID로 직접 입력하게 되어 있습니다

- 새 공지의 입력 이름은 `카테고리 ID`이고 자유 입력칸입니다.
- 카테고리 화면은 이름과 활성 상태만 표시합니다. 생성·수정 기능이 없으며 빈 화면에서는 API로 등록하라고 안내합니다. 입력에 필요한 내부 ID도 표시하지 않습니다.
- 카테고리를 비우면 초안 저장은 가능하지만, 게시 서비스는 카테고리가 없으면 거부합니다.
- 영향: 관리자가 이름을 골라 공지를 분류하고 게시하는 기본 흐름을 화면만으로 완료할 수 없습니다.
- 개선 방향: 카테고리 이름 선택과 화면 내 관리 기능을 제공하고, 게시에 필요한 조건을 미리 알려야 합니다.

### 3. 우선 수정 — 팝업 운영에 필요한 이미지·공지 연결·기간·순서 설정이 없습니다

- 새 팝업 폼과 요청 본문은 국문·영문 제목과 본문 네 값만 다룹니다.
- 이미지 업로드·대체 설명, 연결할 공지 선택, 시작·종료일, 표시 순서가 생성·편집 화면에 없습니다.
- 영향: 행사 이미지 팝업이나 기간 한정 안내를 운영자가 화면에서 설정할 수 없습니다. “공지사항 연결은 선택 사항”이라는 설명과 달리 연결을 선택하는 방법도 없습니다.
- 공지 작성에도 첨부파일과 상단 고정 설정이 없습니다.
- 개선 방향: 실제 운영 시나리오에 필요한 설정을 생성·편집 흐름에 연결해야 합니다. 세부 기능의 API 존재만으로 화면 완성을 판단해서는 안 됩니다.

### 4. 우선 수정 — 국문 초안에 영문 작성을 강제하지만 영문 게시 조작은 없습니다

- 뉴스는 두 언어의 제목·요약·본문, 공지는 두 언어의 제목·본문, 팝업은 두 언어 제목을 필수로 요구합니다.
- 뉴스 생성 서비스와 팝업 저장 서비스도 두 언어 완성을 검사하므로 화면의 필수 표시만 바꾸어서는 충분하지 않습니다.
- 반면 공지·팝업 편집의 게시·게시 중단 요청은 국문으로 고정되어 있습니다.
- 영향: 번역 전 국문만 먼저 저장할 수 없고, 영문을 작성해도 화면에서 영문을 게시할 수 없습니다.
- 개선 방향: 초안 저장은 최소 조건으로 허용하고, 게시할 때 선택한 언어의 완성도를 검사해야 합니다. 팝업 게시 시 해당 언어 제목의 필수 조건은 유지해야 합니다.

- 개선 방향: 현재 편집 내용을 실제 공개 컴포넌트로 확인하는 흐름을 연결해야 합니다.

- 겹침 검사 함수는 있지만 실제 게시 경로에서 호출되지 않습니다.
- 공개 조회는 결과를 앞의 3건으로 자릅니다.
- 영향: 같은 언어의 팝업을 4건 게시하면 관리자에게는 성공으로 처리되지만 공개 대상에서는 일부가 빠질 수 있습니다.
- 확인 수준: API·서비스·저장 경로와 공개 조회의 소스 추적입니다. 실제 데이터 4건을 게시하는 시험은 하지 않았습니다.
- 개선 방향: 게시·예약 확정 전에 겹침 조건을 검사하고, 충돌하는 항목과 기간을 운영자가 알 수 있게 해야 합니다.

근거: [게시 처리](C:/브레인웍스/brainworks.co.kr/src/server/modules/popup-notices/repository.ts:54), [공개 3건 제한](C:/브레인웍스/brainworks.co.kr/src/server/modules/popup-notices/queries.ts:25), [겹침 검사 함수](C:/브레인웍스/brainworks.co.kr/src/server/modules/popup-notices/domain.ts:13), [게시 제한 계약](C:/브레인웍스/brainworks.co.kr/docs/planning/04-admin-and-data/04-02-admin-page-composition.md:350).

### 8. 로컬 실행 오류 — 공지 편집의 날짜 반환값이 직렬화 계약에 맞지 않습니다

- 공지 조회는 DB 날짜 객체를 포함한 행을 반환합니다.
- 편집 페이지는 이를 화면 전달값에 그대로 넣습니다.
- 현재 설치된 Next의 직렬화 검증 함수에 같은 날짜 형태를 넣었을 때 `.notice.createdAt` 직렬화 오류가 재현되었습니다.
- 확인 수준: 프레임워크 검증 함수를 통한 최소 재현입니다. 실제 공지 편집 URL의 인증 후 500 응답을 직접 확인한 것은 아닙니다.
- 현재 설치 버전의 해당 검사는 개발 서버 조건에 연결됩니다. 운영 배포에서도 항상 같은 500이 발생한다고 확대해서 판단하지 않았습니다.
- 개선 방향: 화면에 필요한 필드만 전달하고 날짜를 직렬화 가능한 형태로 변환해야 합니다.

근거: [공지 편집 반환값](C:/브레인웍스/brainworks.co.kr/src/pages/admin/notices/[noticeId].tsx:26), [DB 조회 반환](C:/브레인웍스/brainworks.co.kr/src/server/modules/notices/repository.ts:70), [날짜 필드](C:/브레인웍스/brainworks.co.kr/src/server/db/schema/common.ts:18).

### 9. 운영 전 연결 필요 — 비밀번호 재설정이 실제 이메일 발송으로 이어지지 않습니다

- 인증 설정은 테스트 메일 전송기를 호출합니다.
- 해당 전송기는 메시지를 메모리 배열에 보관하며 실제 이메일을 보내지 않습니다.
- 요청 화면은 응답 성공 여부를 확인하지 않고 전송 안내를 표시합니다.
- 확인 수준: 현재 소스 연결을 확인했습니다. 비밀번호 재설정 요청이나 실제 메일 발송은 수행하지 않았습니다.
- 개선 방향: 운영용 전송기를 연결하고 서버·네트워크 오류와 정상 접수 안내를 구분해야 합니다. 계정 존재 여부를 숨기는 일반 안내 정책은 유지해야 합니다.

## 기존 미완성과 문구 문제

다음은 이번 점검에서 새로 생긴 회귀로 분류하지 않았습니다.

| 대상 | 현재 상태 | 처리 판단 |
|---|---|---|
| 수상 및 인증 | 유형 코드·연도·버전 목록만 있고 생성·수정·공개·순서 변경이 없음 | 승인된 핵심 관리 기능의 미구현입니다. 설명은 관리 가능하다고 표시하여 실제 기능과 어긋납니다. |
| AI 솔루션 | 관리자 화면·메뉴가 없음 | 관리 경로 준비 전 숨기기로 한 결정에 따른 상태입니다. 원래 운영 요구는 남아 있습니다. |
| 계정 설정 | 개발 예정 안내만 있음 | 기존 증빙에 명시된 미완성입니다. 계정 정보 확인·비밀번호 변경을 완료 기능으로 보아서는 안 됩니다. |
| 로그아웃 | 관리자 셸과 전체 소스에서 로그아웃 버튼·호출을 찾지 못함 | UI에서 명시적으로 세션을 끝내는 흐름이 필요합니다. |
| 팝업 이미지 공개 | 조회는 이미지 ID를 반환하지만 공개 컴포넌트는 이미지 URL을 기대 | 9월 2일 문서에도 남은 문제로 기록되어 있습니다. 업로드 UI와 공개 이미지 연결을 함께 확인해야 합니다. |

운영자에게 보이는 문구도 조정할 필요가 있습니다.

- `카테고리 ID`, `API에서 등록`: 이름 선택과 화면 내 등록으로 바꾸는 것이 우선입니다.
- `현재 버전`, `상태 명령을 분리합니다`, `버전을 확인해 주세요`: 내부 구현 설명보다 현재 게시 상태, 수정 시각, 실패 원인과 다음 행동을 안내하는 편이 낫습니다.
- 뉴스의 `슬러그`: 현재 정책상 필요한 공개 주소 식별자이므로 삭제 여부는 별도 결정입니다. 제목 기반 자동 제안과 알아보기 쉬운 설명을 우선 검토할 수 있습니다.
- `수정 내용을 다시 알림`: 방문자의 ‘오늘 보지 않기’를 다시 무효화하는 행동이므로 영향 설명과 확인 단계가 필요합니다. 현재 버튼은 즉시 요청합니다.

## 수정 순서와 재검증 기준

1. 공지·팝업·뉴스의 초안 저장 → 목록 → 수정 → 미리보기 → 선택 언어 게시 흐름을 완성합니다.
2. 카테고리 선택, 팝업 이미지·공지 연결·기간·순서, 공지 첨부를 실제 화면과 서비스에 연결합니다.
3. 게시 제한, 오류 안내, 보관·복원과 세션 관련 흐름을 보완합니다.
4. 수상 및 인증과 AI 솔루션은 기록된 남은 관리 범위로 이어서 구현합니다.

수정 후에는 국문만 준비된 초안, 저장한 초안 다시 열기, 내용 수정, 미게시 미리보기, 언어별 게시, 네 번째 팝업 거부, 종료 예약, 이미지 공개, 보관·복원을 인증된 로컬 DB 환경에서 확인해야 합니다. 최초 점검에서는 수정하지 않았고, 위 후속 보완을 코드에 반영한 뒤 핵심 정책 테스트와 타입 검사를 수행했습니다. 문서 첨부는 악성 파일 검사기가 준비된 뒤 별도 검증해야 합니다.

점검의 보조 기준으로 [웹 인터페이스 가이드라인](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)의 입력 오류 안내, 미저장 변경 보호와 명확한 행동 문구 원칙을 확인했습니다. 구체적인 기능 필요 여부는 프로젝트 문서의 결정을 우선했습니다.
