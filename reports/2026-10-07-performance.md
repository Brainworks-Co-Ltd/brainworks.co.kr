# 홈페이지 성능 측정과 최적화 검토

- 작성일: 2026-10-07
- 기준 코드: `jaewon` `8e2c719`
- 계기: 두 글의 관점을 우리 사이트에 적용해 본다.
  - 「Next.js 이렇게 쓰면 느립니다 1」: 동적 렌더링 라우트는 prefetch가 데이터까지 못 받는다.
  - 「Next.js 이렇게 쓰면 느립니다 2」: Server Function이 순차로 실행된다.
- 방식: 측정 기능을 만들고, 고치기 전과 뒤를 같은 조건에서 실험실 측정으로 비교했습니다.

## 결론

1. **두 글이 말한 손실은 우리 사이트에도 있지만 작습니다.** 정적화한 페이지로 넘어가는 시간이 모바일 조건(왕복 150ms)에서 170\~210ms(23\~31%) 줄었고, 데스크톱에서는 10ms 안팎이었습니다. 운영 서버까지 실제 왕복은 유선 기준 17\~26ms라서, 실제 사용자가 느끼는 차이는 수십 ms 수준으로 봅니다.
2. **더 큰 손실은 첫 진입 화면(LCP)에 있었습니다.** 두 글이 다루지 않는 부분입니다. 모바일 조건에서 홈 LCP가 5.5초(나쁨)에서 1.5초(좋음)로, 뉴스 목록이 2.4초에서 1.4초로 줄었습니다.
3. **권장 순서**
   1. 측정 기능을 먼저 배포해 실제 방문자 기준선을 모읍니다.
   2. LCP 수정(홈 영상, 뉴스 대표 그림)을 도입합니다.
   3. 1편의 정적화(ISR)는 보류합니다. 위험이 없는 쿼리 정리와 `/services` 정적화만 도입합니다.
   4. 관리자 성능 화면의 배포별 비교로 효과를 다시 확인합니다.

## 3. 두 글 관점의 수정 (브랜치 `perf/isr-experiment`)

### 1편: 동적 렌더링 라우트의 prefetch

이 저장소는 App Router가 아닌 Pages Router라서 `cacheComponents`와 `partialPrefetching`은 쓸 수 없습니다. 같은 원리를 Pages Router 방식으로 옮겼습니다. 서버 렌더링 페이지를 `getStaticProps`(ISR)로 바꾸면 prefetch가 데이터까지 미리 받습니다.

**바꾼 것**

- `/services`: DB 조회 결과를 화면에서 쓰지 않고 있어서 조회를 지우고 완전 정적 페이지로 바꿨습니다.
- `/about/honors`, `/news`, `/services/[area]`: ISR로 바꿨습니다.
  - 관리자가 저장하면 그 자리에서 해당 페이지를 다시 만듭니다(on-demand revalidation, 관리자 API 18곳).
  - 재생성 호출이 실패해도 60초 주기로 다시 만드는 안전망을 둡니다.
  - 확인: 관리자 API로 수상 하나를 숨기자 응답(0.26초) 직후 공개 페이지에서 바로 빠졌습니다.
- `/_next/data` 응답에 서버 렌더링과 같은 캐시 헤더를 붙였습니다. 브라우저가 지난 방문의 데이터를 쓰지 않게 하려는 것입니다.
- 배포 스크립트에서 migration을 빌드 앞으로 옮겼습니다. 빌드가 운영 DB를 읽기 때문입니다.

**바꾸지 않은 것**

- 홈과 공지: 팝업과 공지는 게시 시각에 따라 노출이 바뀝니다. 예약 게시를 처리하는 스케줄러가 없어서 정적화하면 공개와 종료가 늦어집니다.
- 공지 목록: 검색과 분류가 주소 query로 동작합니다.
- 뉴스 상세: ISR로 바꿨다가 되돌렸습니다.
  - Next는 404와 리다이렉트 결과를 디스크 캐시에 쓰지 않습니다.
  - 그래서 기사를 숨긴 뒤 서버를 재시작하거나 롤백하면, 첫 요청에 디스크에 남은 예전 본문이 다시 나갑니다(리뷰에서 재현).
  - 숨긴 콘텐츠가 노출되는 문제라 제외했습니다.

### 2편: 순차 실행

우리 사이트에는 Server Action이 없습니다. 같은 관점으로 서버 쿼리를 봤습니다.

- **뉴스 상세**: 서로 독립인 두 쿼리를 `Promise.all`로 묶었습니다.
- **뉴스 목록**: 첫 페이지를 기다린 뒤 나머지 페이지마다 전체 행을 다시 읽던 구조를 쿼리 하나로 바꿨습니다.
  - 기사 수가 N이면 N/12번 돌던 전체 조회가 한 번이 됩니다.
  - `?page=2`로 들어오면 첫 페이지가 빠지고 2페이지가 두 번 실리던 버그도 같이 없어졌습니다.
- **홈**: 화면이 쓰는 뉴스 4건만 읽도록 했습니다.
- **공지 상세**: 두 쿼리가 서로 의존해서 조인이 필요합니다. 이득이 1ms 안팎이라 손대지 않았습니다.

## 5. 자체 검토

### 도입할 가치가 있었나

**1편(정적화)은 효과가 확인됐지만 지금은 도입하지 않는 쪽을 권합니다.**

- 이득: 정적화한 네 종류 페이지로 넘어갈 때 서버 왕복 한 번이 사라집니다.
  - 실험 조건(왕복 150ms)에서는 170\~210ms, 사업 영역 상세는 370ms였습니다.
  - 실제 왕복(유선 17\~26ms, LTE는 대략 40\~70ms로 추정)에서는 수십 ms로, 사람이 차이를 느끼는 선(약 100ms)보다 작습니다.
- 비용
  - 관리자 API 18곳이 공개 페이지 재생성을 책임집니다. 새 관리자 기능을 만들 때마다 이 연결을 빠뜨리면 공개 화면이 늦게 바뀝니다.
  - 재생성이 실패하면 60초가 지난 뒤 첫 방문이 낡은 화면을 받습니다.
  - 404로 바뀌는 페이지에는 쓸 수 없다는 제약을 이번에 확인했습니다(뉴스 상세).
  - 배포 순서가 바뀌어, 앞으로 migration은 열과 테이블 추가만 해야 합니다.
  - 관리자 저장 응답이 페이지 재생성 시간만큼 느려집니다(로컬에서 페이지당 15\~52ms, 솔루션 저장은 8페이지).
  - 승인 문서 5-2의 결정("게시한 내용이 캐시 무효화 작업 없이 다음 요청에서 보인다")을 개정해야 합니다.
- 다시 검토할 조건: 관리자 성능 화면에서 모바일 화면 전환 p75가 해당 경로에서 300ms를 넘으면 실험 브랜치를 그대로 쓸 수 있습니다.

**2편(순차 실행)은 성능 효과를 잴 수 없을 만큼 작았습니다.**

- DB가 같은 서버에 있어 쿼리 하나가 1ms 안팎입니다. 실제로 뉴스 상세 전환 시간은 그대로였습니다.
- 그래도 뉴스 목록의 중복 조회 제거와 `?page=2` 버그 수정은 기사가 늘수록 가치가 있습니다. 위험이 없으니 도입을 권합니다.

### 더 나은 방법이 있었나

**첫 진입 LCP를 고치는 쪽이 효과가 훨씬 컸습니다** (브랜치 `perf/lcp-and-queries`).

  - 첫 화면 영상 묶음에 스크롤 등장 효과(`.bw-reveal`)가 걸려 있었습니다.
  - 이 효과 때문에 JS가 실행될 때까지 투명하게 숨겨져 있었습니다.
  - `industrial.css` 843-844행 주석은 "히어로에는 등장 효과를 겹치지 않는다"고 합니다. 반면 홈 이식 설계(2026-09-16)는 시안의 `Reveal`을 그대로 옮기기로 했습니다. 두 근거가 부딪히므로 디자인 판단이 필요합니다.
- **권장**: 위 표의 앞 다섯 줄을 도입하고, 효과가 없던 두 줄은 뺍니다.
- **손대지 않은 큰 후보**
  - 글꼴 Pretendard: 페이지마다 279\~361KB를 높은 우선순위로 받아 히어로 그림보다 큽니다. 쓰는 굵기와 글자만 남기면 절반 이하로 줄 가능성이 있습니다.
  - 홈 영상: 컷마다 1.7\~1.9MB이고 휴대폰도 같은 파일을 받습니다. 디자인 명세 §16의 "모바일 대용량 미디어 금지"와 어긋납니다.

### 측정의 한계

- 서버는 이 PC에서 돌린 운영 빌드라 운영 서버(RAM 2G)보다 빠릅니다. 서버 처리 시간 차이는 실제보다 작게 나왔을 수 있습니다.
- 로컬 서버는 HTTP/1.1이고 운영 nginx는 HTTP/2입니다.
- 모바일 조건의 TTFB는 믿지 않습니다. CDP 지연은 응답 전달을 늦출 뿐 Navigation Timing에 반영되지 않습니다.
- 데스크톱 홈 LCP(약 2초)는 모든 빌드에서 숨어 있는 다음 영상 컷이 잡힌 값입니다. 실제로 보이는 첫 컷은 그보다 일찍 그려집니다. Google 기준 "좋음"(2.5초 이하) 안이라 더 파지 않았습니다.
- 실험실 숫자는 원인을 가리는 용도입니다. 실제 효과는 배포 뒤 관리자 성능 화면의 배포별 표로 확인해야 합니다.
